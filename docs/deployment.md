# Deployment

OpenFlow has two independently deployable pieces. The server owns model files
and inference processes; the desktop client owns the microphone, shortcut,
overlay, clipboard, and verified macOS Accessibility/Linux AT-SPI text-target
adapters. The server has no keyboard-control API.

## Build the native workers

The default native build uses deterministic mock backends for development. A
production build uses isolated CMake trees so each upstream keeps its own ggml
revision:

```sh
cmake -S native -B build/native-asr \
  -DCMAKE_BUILD_TYPE=Release \
  -DOPENFLOW_ENABLE_WHISPER_CPP=ON \
  -DOPENFLOW_WHISPER_CPP_DIR=/path/to/whisper.cpp \
  -DOPENFLOW_ENABLE_LLAMA_CPP=OFF \
  -DGGML_CUDA=ON
cmake --build build/native-asr --parallel --target openflow-asr-worker

cmake -S native -B build/native-llm \
  -DCMAKE_BUILD_TYPE=Release \
  -DOPENFLOW_ENABLE_WHISPER_CPP=OFF \
  -DOPENFLOW_ENABLE_LLAMA_CPP=ON \
  -DOPENFLOW_LLAMA_CPP_DIR=/path/to/llama.cpp \
  -DGGML_CUDA=ON
cmake --build build/native-llm --parallel --target openflow-llm-worker
```

Use `GGML_METAL=ON` on Apple Silicon or `GGML_VULKAN=ON` where appropriate.
Place `openflow-server`, `openflow-asr-worker`, and `openflow-llm-worker` in the
same directory, or configure the worker paths explicitly. A self-contained
desktop installation also places `openflow-server` beside the desktop executable;
the client then starts it on loopback and captures a fresh installation's
one-time bootstrap credential without writing it to logs.

### Build installers

The supported release wrapper builds those three binaries, stages them with the
target-triple suffix required by Tauri, verifies that they have no build-local
dynamic-library references, and applies a release-only Tauri configuration:

On Ubuntu 24.04, install the desktop and Vulkan build prerequisites first:

```sh
sudo apt-get install build-essential cmake ninja-build \
  libwebkit2gtk-4.1-dev libappindicator3-dev librsvg2-dev libasound2-dev \
  libvulkan-dev glslc spirv-headers patchelf rpm
```

```sh
# macOS: Metal workers, .app.zip, and .dmg
./scripts/build-installers.sh

# Linux: Vulkan workers, AppImage, .deb, and .rpm
./scripts/build-installers.sh
```

The ASR and cleanup workers use isolated CMake build trees because the pinned
`whisper.cpp` and `llama.cpp` releases each carry their own ggml revision. The
resulting static workers are combined only at the installer-staging boundary.

Production builds fetch the reviewed `whisper.cpp` and `llama.cpp` release tags
and require them to resolve to the immutable full commits in
`packaging/upstream.env`. To build from already audited checkouts without
network access, set both source paths:

```sh
OPENFLOW_WHISPER_CPP_DIR=/source/whisper.cpp \
OPENFLOW_LLAMA_CPP_DIR=/source/llama.cpp \
./scripts/build-installers.sh --profile cpu
```

Supported inference profiles are `metal`, `vulkan`, `cuda`, `rocm`, and `cpu`;
`auto` chooses Metal on macOS and Vulkan on Linux. The standard downloadable
Linux installer uses Vulkan because it supports consumer GPUs across vendors.
Use `rocm` for an AMD Linux host with HIP/ROCm and `cuda` for a controlled
NVIDIA deployment. Those vendor-specific bundles depend on a compatible system
runtime, so they are built for the target machine rather than published as the
generic Linux installer. GPU drivers remain a system prerequisite for every
profile.

Artifacts are collected under `dist/release/<target-triple>/`. A normal 0.1.0
build produces:

- `OpenFlow_0.1.0_aarch64.dmg` and
  `OpenFlow_0.1.0_aarch64-apple-darwin.app.zip` on Apple Silicon;
- `OpenFlow_0.1.0_x64.dmg` and
  `OpenFlow_0.1.0_x86_64-apple-darwin.app.zip` on Intel macOS;
- `OpenFlow_0.1.0_amd64.AppImage`, `OpenFlow_0.1.0_amd64.deb`, and
  `OpenFlow-0.1.0-1.x86_64.rpm` on x86-64 Linux;
- `OpenFlow-server_0.1.0_x86_64-unknown-linux-gnu.tar.gz`, containing the three
  production server executables, service template, environment example, and
  dependency licenses for a headless Linux model host;
- an SPDX JSON SBOM when `syft` is installed, plus `SHA256SUMS` in every output
  directory.

The exact platform package name is ultimately generated by the pinned Tauri
CLI and is checked by the build wrapper rather than assumed. Model weights are
not embedded in any installer; selecting one downloads it into the server cache.

Use `--mock-native` only to validate packaging without real inference. Such an
installer is not a release candidate.

### Arch Linux with ROCm

The Arch builder creates an unprivileged application directory and `.tar.zst`
containing the desktop, server, both real workers, notices, and dependency
licenses. It uses Arch's native ROCm packages; Arch is not in AMD's upstream
supported-distribution matrix, so keep the system packages and kernel driver in
sync and retain the Vulkan profile as a fallback.

```sh
sudo pacman -S --needed base-devel cmake nodejs npm rustup \
  webkit2gtk-4.1 libappindicator alsa-lib \
  zstd rocm-hip-sdk hip-runtime-amd rocblas hipblas
rustup default stable

# The builder normally detects the ISA with rocminfo. For an RX 7600, pin it:
OPENFLOW_AMDGPU_TARGETS=gfx1102 \
  ./scripts/build-arch-bundle.sh --profile rocm
```

Before launching, `rocminfo` must succeed for the desktop user and `/dev/kfd`
plus the matching `/dev/dri/renderD*` node must be accessible. After changing
`video` or `render` group membership, log out and back in. Extract and run:

```sh
tar --zstd -xf dist/arch/OpenFlow-0.1.0-rocm-x86_64.tar.zst
cd dist/arch/OpenFlow-0.1.0-rocm-x86_64
./openflow-desktop
```

If ROCm cannot initialize this card/driver combination, rebuild with
`--profile vulkan`; model files are backend-independent and remain reusable.

### Signing and automated releases

Pushing a matching `vX.Y.Z` tag runs `.github/workflows/release.yml`, builds
Linux x86-64 plus Apple Silicon and Intel macOS installers, creates an SPDX SBOM
and checksums, attests public-repository artifacts, and creates a **draft**
GitHub release. Publishing the draft remains a deliberate maintainer action.
Release tags are gated by the complete Rust, native-worker, frontend, formatting,
test-layout, and strict-Clippy suites before platform packaging begins.

For a macOS release accepted by Gatekeeper, configure these GitHub Actions
secrets:

- `APPLE_CERTIFICATE`: base64-encoded Developer ID Application `.p12`;
- `APPLE_CERTIFICATE_PASSWORD`: the `.p12` export password;
- `APPLE_SIGNING_IDENTITY`: optional exact Keychain identity (Tauri can infer
  it from the certificate);
- `APPLE_ID`: the notarization Apple account;
- `APPLE_PASSWORD`: an app-specific password, not the account password;
- `APPLE_TEAM_ID`: the Apple Developer team identifier.

With no certificate, CI deliberately creates an ad-hoc signed macOS preview and
emits a warning. It may require manual approval in Privacy & Security and must
not be presented as a notarized release. With a Developer ID certificate but
incomplete notarization credentials, the workflow fails instead of emitting a
partially signed release.

For a local signed build, install the Developer ID certificate in the login
Keychain, set `APPLE_SIGNING_IDENTITY`, plus either the three Apple-ID
notarization variables above or Tauri's App Store Connect API-key variables,
and run the same installer script. Linux package repository signing is separate
from building the `.deb`/`.rpm`; downstream repositories should sign their
repository metadata with their own maintained key.

OpenFlow does not yet embed an automatic updater or a project package-repository
trust root. Install upgrades from a release artifact after verifying its
`SHA256SUMS`; do not present an ad-hoc macOS preview as a notarized release.

## Local server

The desktop defaults to `http://127.0.0.1:8765`. Start the service with:

```sh
OPENFLOW_ASR_WORKER=/path/to/openflow-asr-worker \
OPENFLOW_LLM_WORKER=/path/to/openflow-llm-worker \
OPENFLOW_WORKER_BACKEND=auto \
cargo run --release -p openflow-server
```

When launched as a desktop-managed child, the server rotates its administrator
credential on every launch and writes one bootstrap JSON object to the
protected standard-output pipe; the client immediately stores that credential
in the OS secret store. An independently managed server emits a bootstrap
credential only on its first start. When starting that service manually, paste
the object's `admin_token` into the desktop connection page. Normal logs go to
standard error and never contain credentials, audio, or transcripts. Set
`OPENFLOW_ADMIN_TOKEN` to a stable secret of at least 24 characters when a
service manager owns the process.

Selecting a model in the desktop starts a resumable download on the server.
The server pins the upstream revision, verifies byte length and SHA-256, and
atomically promotes the file into its cache. Downloads can be cancelled; the
verified partial `.part` file is retained so selecting the model again resumes
instead of restarting. Model licenses remain upstream licenses and are
displayed by the client.

## Remote server

The Linux release directory includes a standalone server archive. Its
`README.md`, systemd unit, and environment example keep the model host separate
from the desktop client. The desktop model library remains the management UI:
once paired, it can select, download, cancel, activate, or delete models on that
host.

For a direct listener, set `OPENFLOW_BIND` plus both `OPENFLOW_TLS_CERT` and
`OPENFLOW_TLS_KEY`. OpenFlow rejects a non-loopback bind without TLS. Keep the
application bearer authentication enabled even behind a private network.

For Tailscale Serve, keep OpenFlow on loopback and proxy it inside the tailnet:

```sh
tailscale serve --bg http://127.0.0.1:8765
tailscale serve status
```

Create a short-lived pairing code with an administrator credential, exchange
it once on the client, then use the returned device token:

```sh
curl -X POST https://SERVER/v1/pairing-codes \
  -H 'Authorization: Bearer ADMIN_TOKEN'

curl -X POST https://SERVER/v1/pair \
  -H 'Content-Type: application/json' \
  -d '{"pairing_code":"CODE","device_name":"My laptop"}'
```

Each device can be revoked independently. The server accepts multiple paired
idle clients but grants only one active dictation lease at a time. Pair only
trusted devices: a paired-device credential deliberately includes model-cache
management, so it can consume server bandwidth/storage or replace the active
model pair. Pairing-code and device-revocation administration remains restricted
to the administrator credential.

### Arch model host and MacBook client

Run the Arch server independently rather than allowing the Arch desktop to own
its lifecycle. The extracted ROCm bundle includes a foreground host launcher
that creates private durable state and starts both workers automatically:

```sh
./openflow-host
```

Leave that terminal open. `openflow-host` stores its administrator credential
at `$XDG_DATA_HOME/openflow-server/admin-token` (or the corresponding
`~/.local/share` path) with user-only permissions; routine pairing does not
require viewing or copying it. Models and approved devices persist across host
restarts. The foreground launcher prints finalized raw Whisper transcripts and
any differing cleaned transcript for local diagnostics. Because those lines can
contain sensitive dictated text, use `OPENFLOW_PRINT_TRANSCRIPTS=0 ./openflow-host`
to disable them. The background server does not print transcript content unless
`OPENFLOW_PRINT_TRANSCRIPTS=1` is explicitly configured.

In another Arch terminal, join Tailscale and publish only the loopback service:

```sh
sudo pacman -S --needed tailscale
sudo systemctl enable --now tailscaled
sudo tailscale up
tailscale serve --bg http://127.0.0.1:8765
tailscale serve status
```

On the MacBook, install the OpenFlow macOS client, join the same tailnet, choose
**Remote server**, enter the HTTPS `*.ts.net` URL shown by `tailscale serve
status`, set a recognizable device name, and choose **Request server approval**.
The client shows a six-digit code while it waits. Verify the same device name
and code in the Arch server terminal and answer `y`; any other request should be
denied with `n`. The returned device credential is stored in macOS Keychain and
remains valid through client and server restarts until revoked.

Model selection and downloads in the Mac UI operate on the Arch cache;
microphone audio travels to Arch and transcript events return to the Mac, where
Accessibility insertion remains entirely client-side. Grant the Mac app both
Microphone and Accessibility permissions. A macOS `.dmg` must be built on macOS
or downloaded from the macOS release workflow; the Arch builder cannot produce
or sign it.

The foreground launcher is intentionally interactive. Tailscale Serve continues
in the background independently, so it does not require backgrounding OpenFlow.
For unattended boot, run `openflow-server` with the documented systemd unit and
leave `OPENFLOW_INTERACTIVE_PAIRING` unset; existing paired clients keep working,
and new clients use the administrator-created one-time-code flow above.

## Memory selection

The bundled catalog contains Whisper Large v3 Turbo Q8 and Large v3 Q5 plus
Qwen3 1.7B Q8, 4B Q4_K_M, and 8B Q4_K_M. Recommendations reserve 20% of the
reported memory and then prefer the largest cleanup model and ASR model that
fit together. Linux automatically uses the largest single GPU reported by DRM
sysfs or `nvidia-smi`. Set `OPENFLOW_ACCELERATOR_MEMORY_BYTES` to the usable
VRAM byte count when detection is unavailable, when the server is containerized,
or to enforce a lower operational ceiling. The default 10 GB tier is Turbo plus
Qwen3 4B; larger cards can select Large v3 plus Qwen3 8B. The server
independently enforces this 80% budget when a session starts, so a modified or
older client cannot activate an oversized pair.
Only accelerators compiled into both selected production workers are advertised.
A CPU package uses system memory for recommendations even on a GPU-equipped host.
